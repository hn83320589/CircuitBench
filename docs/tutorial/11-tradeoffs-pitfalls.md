## 設計取捨

### 取捨 1：暫態積分用 TR + BE／BDF2 混合，而不是單一方法

- **決策**：平時用 TR；t = 0、轉折點之後與偵測到交替時，改用 BE 與 BDF2。
- **考慮過的選項**：
  - 單用 TR：會在剛性模態交替。
  - 單用 BDF2：每一步都損失能量。
  - TR-BDF2：每步內混合兩種方法。
- **選擇與理由**：📄 README「設計取捨」：L-stable 方法在 LC 振盪中每一步都會損失能量，以 ωh = 0.2 計，BDF2 每步約損失 0.07%，100 個週期就遠超過 1%。TR 能量守恆，但遇到剛性模態會交替。混合策略才能同時滿足驗收標準 8～12。規劃階段（📄 規劃文件「風險 4」）原本把 TR-BDF2 列為備案。
- **代價**：
  - 方法切換的狀態機增加了複雜度。
  - 「非轉折點的剛性」需要額外的反向偵測（見踩坑 1）。

### 取捨 2：圖面文件不可變

- **決策**：`SchematicDocument` 是 record + `ImmutableList`，每次編輯都回傳新物件。
- **考慮過的選項**：可變模型 + 命令模式（每個操作寫 Do／Undo）。
- **選擇與理由**：📄 README：復原只要保存快照，「復原後網表必然相同」天然成立。
- **代價**：每次編輯都配置新清單。教學規模可以忽略，但萬級元素時要重新評估。

### 取捨 3：接腳碰到導線中段也算相連

- **決策**：接腳落在導線中段時，與導線端點落在中段同樣處理，自動產生接點。
- **選擇與理由**：📄 規劃決策 D2；README：與導線端點的規則一致，學生比較不會困惑。
- **代價**：元件畫在導線上時會被短路，但圖上會看到接點，學生看得出來。

### 取捨 4：節點上限只在 UI 端強制

- **決策**：編輯器與網表匯入限制 5,000 個節點（`CircuitValidator.MaxNodes`）；Core 本身不設上限。
- **選擇與理由**：📄 規劃決策 D1。需求規格同時要求「單一電路最多 5,000 節點」與「100×100 電阻網格（1 萬個未知數）的效能測試」，兩者衝突。所以上限放在 `CircuitValidator`（分析前的檢查，UI 一定會經過），而 `Simulator` 本身不檢查；效能測試直接呼叫 `Simulator`，不經過檢查。`CircuitValidator.Validate()` 另外提供 `enforceNodeLimit: false` 參數，可以只略過這一項檢查。
- **代價**：Core 的使用者要自己決定上限。

### 取捨 5：參數保存為字串

- **決策**：圖面與專案檔保存 `"4.7k"`，萃取網表時才解析。
- **選擇與理由**：📄 README：保留學生輸入的寫法；參數錯誤時，檢查能指出是哪個元件。
- **代價**：每次萃取都要重新解析。數量很少，可以忽略。

### 取捨 6：trtol 預設為 1（SPICE 為 7）

- **選擇與理由**：📄 README：暫態點數約多一倍，但 RC 步階響應與整流波形的誤差能穩定落在驗收門檻內。
- **代價**：點數與執行時間增加。

### 取捨 7：預設就限制振盪與驅動訊號的步長

- **決策**：SIN 每週期至少 50 點、自由振盪每週期約 100 點，另加折線內插誤差控制。
- **考慮過的選項**：維持原樣，在 README 建議使用者自己調小最大步長。這是初版的做法，見踩坑 4。
- **選擇與理由**：📄 審查回饋與 README：學生用預設值就要看到準確、平滑的波形。
- **代價**：半波整流 2 個週期從 60 點增加到約 760 點；教學規模的電路仍只要幾十毫秒。

### 取捨 8：波形曲線不做反鋸齒

- **選擇與理由**：📄 README：每個像素欄本來就是一條垂直線段，反鋸齒的畫質差異很小，卻占了大部分光柵化時間。關掉後，完整重繪的平均時間從 12 ms 降到約 5 ms。
- **代價**：斜線邊緣有鋸齒，但在波形密集時幾乎看不出來。

### 取捨 9：不使用 DI 容器、FsCheck、FakeTimeProvider

- **選擇與理由**：📄 規劃文件與 README：Composition Root 只有十幾行；性質測試 harness 與 `ManualTimeProvider` 自己寫，容易控制種子與訊息格式，也少了套件相依。
- **代價**：要自己維護約 100 行的測試基礎設施。

### 取捨 10：SourceSpec 採用 SPICE 語意

- **決策**：沒有暫態函數時，暫態沿用直流值；沒有直流值時，直流工作點取波形在 t = 0 的值。
- **選擇與理由**：📄 README：讓網表匯出再匯入後能完全相同。
- **代價**：不熟 SPICE 的學生可能不知道「只寫 SIN 時，直流工作點用的是 SIN(0)」。

## 踩坑紀錄

### 踩坑 1：開關電感範例出現 TR 逐步正負交替（不在轉折點上）

- **症狀**：製作範例 08（開關切換的電感）時，開關打開後，電流經飛輪二極體降到 0 的那一刻，某個節點電壓開始一正一負地交替。
- **原因**：二極體截止使節點變成極高阻抗，這是剛性模態。但這個時刻**不是轉折點**，原本「轉折點後改用 BE／BDF2」的機制不會觸發，TR 在剛性模態下就會交替。
- **解法**（📄 commit `881c8f0`）：TR 的某個未知數反向時，以 BDF2 重算同一步；兩者在反向的未知數上相差超過容許值 10 倍時，判定為 TR 振盪，改用 BDF2 的結果。**只比對反向的未知數**，避免 LC 正常極值處被誤判而損失能量。回歸測試為 `StiffnessAppearingWithoutBreakpointDoesNotRing`。
- **教訓**：範例電路不只是交付物，也是很好的測試。手算預期值加上自動驗證，能抓到單元測試沒想到的組合。

### 踩坑 2：同一矩陣元素內的抵消沒被偵測（審查回饋，最嚴重）

- **症狀**：審查者的網表（I1、R1 3k、G1 −1/3k）通過全部電路檢查，卻得到 V(n1) = 3.07e15 V，沒有任何錯誤。審查者另外測試 44 個秩虧 1 的隨機矩陣，有 22 個被當成正常矩陣求解。
- **原因**：奇異判定的尺度是「這一欄抵消後的最大值」。抵消發生在同一個元素內時，殘值本身就是最大值，判定永遠不會成立。另外，多步消去累積的捨入誤差也可能蓋過固定門檻。
- **解法**（📄 commit `2654d70`）：
  - 組裝時記錄每個元素抵消前的量級，作為主元判定的尺度。
  - 求解後再算列縮放條件數下界，超過 1e12 就回報接近奇異。
  - 錯誤訊息列出相關元件與「負電阻剛好抵消」這個可能原因。

  詳見 08 章第 5 節。
- **教訓**：
  - **「通過檢查」不等於「數值上可解」**。結構檢查（union-find）只看拓樸，看不到數值上的抵消。
  - 原本的性質測試只測「結構奇異」與「良態」兩種矩陣，缺少「數值秩虧」的案例。修正時補上了 300 個秩虧矩陣的性質測試，以及反向的「不誤報」測試。

### 踩坑 3：「重繪 ≤ 16 ms」原本沒量到 Skia 實際繪製

- **症狀**：初版的效能測試只量了 ViewModel 的抽樣與刻度計算（最差 5.5 ms），被審查指出沒有包含 Skia 的實際繪製時間。
- **原因**：規劃階段認為 Headless 的計時與實機 GPU 不同，所以沒有自動化量測（📄 規劃文件「風險 6」）。
- **解法**（📄 commit `b0dcbc8`）：新增 `RenderPerformanceTests`，以 `RenderTargetBitmap` 讓 Skia 實際光柵化 1750×899 的波形畫布。**第一次量測就發現最差 23.5 ms，確實超標**。之後做了三項最佳化：
  - 快取刻度文字的 `FormattedText`，`Pen` 改為共用。
  - 曲線改為非反鋸齒。
  - 抽樣結果寫入重用的緩衝區，減少 GC 停頓（`WaveformViewModel.ColumnsInto()`）。

  優化後平均約 5 ms，最差 10–15 ms。
- **教訓**：**沒有量測的效能宣稱就是沒有驗證**。「只量容易量的部分」是常見的盲點，量了之後才發現真正的瓶頸在文字排版與 GC，而不是演算法。

### 踩坑 4：預設設定下 RLC 頻率誤差超標

- **症狀**：欠阻尼 RLC 在預設設定下，頻率誤差 0.43%、衰減率誤差 1.39%，超過 0.2%。初版的處理方式是在 README 建議「振盪電路把最大步長設為週期的 1/100」，並在測試中手動設定，判定為「附條件通過」。
- **原因**：LTE 控制的是每一步的局部誤差，不是長時間累積的相位誤差。另外，純電阻電路沒有狀態量，LTE 恆為 0，步長完全不受控。
- **解法**（📄 commit `1568d1c`）：加入三道自動步長上限（見 08 章 7.4），測試改用預設設定。
- **教訓**：使用者是學生，「需要手動調參數才準確」等於不準確。驗收標準雖然沒寫「預設設定」，但從使用者是誰就可以推出這個要求。

### 踩坑 5：工程記號的指數溢位丟出例外

- **症狀**：`EngineeringNotation.TryParse("1e99999999999k")` 丟出 `OverflowException`，網表匯入因此崩潰。
- **原因**：指數以 `int.Parse` 解析，違反了 `TryParse` 不丟例外的約定。
- **解法**（📄 commit `cf9cf3a`）：改用 `long.TryParse` 並限制指數範圍；極大值回報為超出範圍，極小值視為 0。網表讀取另外把非預期的格式例外轉成該行的錯誤。
- **教訓**：`TryXxx` 方法內部只要呼叫任何會丟例外的 API，就要逐一檢查。這個問題是自動安全審查找到的，模糊測試（fuzzing）類的輸入很適合找這種問題。

### 踩坑 6：專案檔可以載入未定義的元件類型

- **症狀**：專案檔中 `"kind": 99` 這類整數或未定義的列舉值能被 System.Text.Json 接受，之後在繪製或萃取時才崩潰。
- **原因**：System.Text.Json 預設接受任何整數作為列舉值，不檢查是否有定義。
- **解法**（📄 commit `88faf09`）：載入時以 `Enum.IsDefined()` 拒絕未定義的列舉值，也拒絕 null 參數值，回傳 `Corrupted`。
- **教訓**：反序列化的驗證要在**邊界**一次做完。讓不合法的資料進入系統內部，錯誤就會在遠離來源的地方爆發，很難追查。

### 踩坑 7：TestKit 被當成測試專案，CI 第一次就紅燈

- **症狀**：CI 的 `dotnet test` 在 TestKit 上 testhost 失敗。
- **原因**：TestKit 參考了 xunit 套件，SDK 就把它當成測試專案。
- **解法**（📄 commit `a02f782`）：在 csproj 檔明確設定 `IsTestProject=false`。
- **教訓**：本機只跑個別測試專案時看不到這個問題，要在 solution 層級執行 `dotnet test`，才會跟 CI 一致。

### 踩坑 8：波形邊緣的假尖刺

- **症狀**：Headless 截圖中，快速上升的波形邊緣出現往回拉的細線，看起來像尖刺。
- **原因**：每欄固定先畫 max 再畫 min，相鄰欄連線時會多走一段。
- **解法**（📄 commit `66297ca`）：先連到離上一點較近的一端。
- **教訓**：用 Headless 產生真實截圖並實際**看過**，能找到數值測試抓不到的視覺問題。

### 踩坑 9：Headless 關閉視窗時當機

- **症狀**：Headless 測試結束、關閉主視窗時當機。
- **原因**：關閉前的「未儲存確認」原本在 View 裡直接開對話框，Headless 下沒有人能按。
- **解法**（📄 commit `66297ca`）：確認邏輯移到 `MainWindowViewModel.ConfirmCloseAsync()`，透過 `IMessageService`；測試注入 `NullDialogs`。
- **教訓**：任何會「等使用者」的動作都要經過服務介面，否則它會成為自動化測試的死結。
